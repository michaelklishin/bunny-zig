# Instructions for AI Agents

## What is This Codebase?

This is a Zig client library for RabbitMQ that implements AMQP 0-9-1. It is heavily inspired by
[Ruby Bunny](https://github.com/ruby-amqp/bunny), [`bunny-swift`](https://github.com/michaelklishin/bunny-swift) (a Swift 6 port),
and [`bunny-rs`](https://github.com/michaelklishin/bunny-rs) (a Rust port).


## Build and Test

```bash
zig build

zig build test

zig build test -- --test-filter "pattern"
```

### Test Node Configuration

Integration tests require a RabbitMQ node running on `localhost:5672` with default credentials (`guest`/`guest`).

Unit tests (protocol encoding/decoding, field tables, properties) do not require a running RabbitMQ node.


## Repository Layout

 * `src/`: contains the Zig source code
   * `src/protocol/`: AMQP 0-9-1 wire format: frame codec, method definitions, field tables, properties
   * `src/`: connection, channel, exchange, queue, consumer, transport, recovery
 * `tests/`: contains integration tests that require a running RabbitMQ node


## Key Files

 * `src/connection.zig`: `Connection`, `ConnectionOptions`, connection lifecycle and heartbeat management
 * `src/channel.zig`: `Channel`, RPC dispatch, delivery routing, acknowledgements
 * `src/exchange.zig`: exchange declare, delete, bind, unbind
 * `src/queue.zig`: queue declare, delete, bind, unbind, purge
 * `src/consumer.zig`: push consumer, message delivery, cancellation
 * `src/confirm.zig`: publisher confirm tracking
 * `src/transport.zig`: TCP and TLS transport abstraction
 * `src/recovery.zig`: automatic connection recovery and topology replay
 * `src/protocol/frame.zig`: frame encoding and decoding
 * `src/protocol/method.zig`: AMQP method definitions and serialization
 * `src/protocol/types.zig`: field tables, field values, AMQP type system
 * `src/protocol/properties.zig`: BasicProperties with flag-based serialization
 * `src/protocol/constants.zig`: frame types, class/method IDs, reply codes, defaults


## Code Style

 * Target Zig 0.16.0+
 * Use `std.log` scoped logging for diagnostics
 * Prefer explicit error handling with Zig error unions over panics
 * Use `errdefer` for cleanup on error paths
 * Keep allocator-awareness: accept `std.mem.Allocator` parameters, never use a global allocator
 * Prefer slices over sentinel-terminated pointers when possible
 * Use packed structs for wire-format structures where appropriate
 * Naming: `camelCase` for functions and locals, `PascalCase` for types, `snake_case` for file names


## Tests

 * Tests should be descriptive and easy to read
 * Use property-based style tests (roundtrip encode/decode) for protocol types
 * Integration tests go in `tests/` and require a running RabbitMQ node
 * Unit tests for protocol encoding/decoding are inline (`test` blocks) next to the implementation
 * Use `std.testing.expectEqual`, `std.testing.expect`, and `std.testing.expectEqualSlices` for assertions


## Comments

 * Only add important comments that express the non-obvious intent, both in tests and in the implementation
 * Keep the comments short
 * Pay attention to the grammar of your comments, including punctuation, full stops, articles, and so on

## Releases

### How to Roll (Produce) a New Release

Suppose the current development version in `build.zig.zon` is `0.N.0` and `CHANGELOG.md` has
a `## 0.N.0 (in development)` section at the top.

To produce a new release:

 1. Update the changelog: replace `(in development)` with today's date, e.g. `(Feb 20, 2026)`. Make sure all notable changes since the previous release are listed
 2. Commit with the message `0.N.0` (just the version number, nothing else)
 3. Tag the commit: `git tag 0.N.0`
 4. Bump the dev version: back on `main`, set `build.zig.zon` version to `0.(N+1).0`
 5. Add a new `## 0.(N+1).0 (in development)` section to `CHANGELOG.md` with `No changes yet.` underneath
 6. Commit with the message `Bump dev version`
 7. Push: `git push && git push --tags`

## After Completing a Task

After completing a task, look very carefully for gaps in the implementation, the test coverage,
missed opportunities to use idiomatic Zig patterns, meaningful optimizations on the common code paths,
and more ways to lean on the Zig type system for additional safety.

Reducing duplication is good unless it makes the codebase more complex.

"There's nothing meaningful to improve" is an acceptable answer.
